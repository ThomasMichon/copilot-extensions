# Historical project-command reconciliation

`reconcile-binstubs` uses the existing per-command ownership locks and receipt
ledger. It refreshes registered commands and retires attributable unregistered
or `knowledge_only` commands. It does not activate installation cells or
transfer another installation's commands.

Automatic physical relocation requires a matching installation receipt and
marketplace identity, the same runtime root and source repository, and a
non-decreasing payload version. Legacy snapshots have a narrower bridge:
`<runtime>/snapshots/<version>/plugin.json` must match the plugin, repository and
version, and the runtime's deployment manifest must name the exact selected
current payload source. This bridge cannot adopt a legacy command into a cell.
Registered relocation also checks the project's current name, path and remote.
Other relocations remain explicit ownership blockers.

Pre-receipt admission compares complete generated bytes against the known
payload-pinned, traced and ambient-project template families. A marker, familiar
publisher, plugin name or isolated routing line is insufficient. Historical
LF/CRLF forms are accepted; additional commands or altered siblings are not.
Without a receipt, cell ownership cannot be inferred. Unknown or corrupt
receipts never authorize automatic transfer.

All existing platform siblings are checked together, including a Windows
`.ps1` whose generated header was edited away. Missing siblings can be repaired;
an edited sibling protects the entire command. Obsolete retirement uses the
same validation and recovery boundary.

Publication first records prior bytes, file modes and intended bytes/receipt
inside the existing receipt's optional `transaction` section. Each file is
published by atomic replacement, then the final receipt is published. An
ordinary publication failure restores prior usable bytes and receipt. After a
process interruption, retry finishes only when ownership and registered
identity still match and every existing sibling matches the recorded prior or
intended bytes. Edited intermediate files or corrupt transactions remain
precise blockers. This is recoverable multi-file publication, not a promise of
one atomic filesystem operation across a Windows command pair.

Results retain `migrated`, `removed` and `preserved`. `blocked` identifies
unresolved **required** commands: registered commands (including knowledge-only
retirement) and admitted-owned obsolete commands whose retirement remains
unfinished, even after unregistration. Recovery retains required status once
the pending transaction's ownership and structure are verified; publication
errors or edited intermediate bytes cannot turn owned cleanup into advisory
inventory. Unrelated foreign or ambiguous unregistered inventory remains advisory in
`preserved`. A required blocker suppresses the “in sync” message. Consumers
must use `blocked`, not assume that zero changed files proves convergence.
An unchanged second pass leaves both command and receipt timestamps untouched.
