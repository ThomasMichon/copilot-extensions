# Historical project-command reconciliation

`reconcile-binstubs` uses the existing per-command ownership locks and receipt
ledger. It refreshes registered commands and retires attributable unregistered
or `knowledge_only` commands. It does not activate installation cells or
transfer another installation's commands.

Before pruning or touching commands, reconciliation acquires one strict projects
snapshot under the existing registry lock. It validates target names, entries
and case collisions, and reuses that snapshot for pruning and deployment.
Unreadable or malformed authoritative input fails explicitly without command,
receipt or prune writes. Missing registry input with prior command inventory
also blocks; an empty target set with prior inventory must be explicitly
declared as `projects: {}`. An absent registry remains supported for a fresh
installation with no prior commands or receipts. Tolerant read-only views do
not authorize retirement.
Both the shared registry reader and the secondary explicit-empty check reject
duplicate YAML mapping keys at every nesting level before schema migration or
defaulting. A later `projects: {}` cannot override an earlier populated target
set and authorize retirement. Tolerant read-only callers retain their existing
empty-view fallback, but mutation always reports invalid input explicitly.

Cell-scoped physical relocation requires a matching installation receipt and
marketplace identity, the same runtime root and source repository, and a
non-decreasing payload version. Legacy snapshots have a narrower bridge:
`<runtime>/snapshots/<version>/plugin.json` must match the plugin, repository and
version, and the runtime's deployment manifest must name the exact selected
current payload source. Checkout-to-marketplace adoption is also automatic for
an unchanged receipted command belonging to the same legacy runtime, plugin and
repository, with a non-decreasing version and a deployment manifest naming the
exact selected marketplace payload and version. The old checkout need not
remain on disk. Neither legacy bridge can adopt a command into a cell.
Registered relocation also checks the project's current name, path and remote.
Other relocations remain explicit ownership blockers.

Legacy shortcuts converge to the installed user-side command in their resolved
local-bin directory; cell shortcuts remain payload-local. Native install/update
flows publish the verified activated runtime's manifest before registration and
reconciliation, so adoption sees the new source rather than the prior checkout.

Pre-receipt admission compares complete generated bytes against the known
payload-pinned, traced and ambient-project template families. A marker, familiar
publisher, plugin name or isolated routing line is insufficient. Historical
LF/CRLF forms are accepted; additional commands or altered siblings are not.
Without a receipt, cell ownership cannot be inferred. Unknown or corrupt
receipts never authorize automatic transfer.
User-side shortcut bytes contain no owner identity and cannot authorize
receipt-free adoption or retirement.

All existing platform siblings are checked together, including a Windows
`.ps1` whose generated header was edited away. Missing siblings can be repaired;
an edited sibling protects the entire command. Obsolete retirement uses the
same validation and recovery boundary.
Windows removal resolves registered spelling before rendering templates.
Recovery normalizes both journal sibling maps case-insensitively, including
receipt-only retirement, while rejecting duplicate aliases and unexpected names.

Publication first records prior bytes, file modes and intended bytes/receipt
inside the existing receipt's optional `transaction` section. Each file is
published by atomic replacement, then the final receipt is published. An
ordinary publication failure restores prior usable bytes and receipt. After a
process interruption, retry finishes only when ownership and registered
identity still match and every existing sibling matches the recorded prior or
intended bytes. Edited intermediate files or corrupt transactions remain
precise blockers. This is recoverable multi-file publication, not a promise of
one atomic filesystem operation across a Windows command pair.
Every command replacement, deletion and permission change revalidates the
affected sibling against admitted prior/intended bytes immediately before
mutation, including after staging a replacement. Publication, recovery and
rollback also verify the complete resulting pair before settling the receipt.
Unexpected interleaved edits are preserved, fail visibly and retain the
journal; retries remain blocked until the recorded state is restored. These
checks are not atomic filesystem compare-and-swap against uncooperative writers.
Admission reads each sibling's bytes once and performs receipt/template checks
against those captured bytes. `validate()` returns immutable `CommandAdmission`
evidence; its truthiness retains the historical-migration indicator. Explicit
transfer instead captures the specific authorized bytes with `admit_transfer()`.
Installer preflight, reconciliation and retirement carry that evidence to
`publish(admitted=...)` without recapturing authority. Publication compares its
working snapshot against the evidence before writing a journal: changed or
newly appeared bytes are preserved and rejected, not adopted as a new prior
state. Missing admission evidence fails closed rather than triggering an
implicit fresh validation.
An explicitly authorized transfer journals the destination owner, project and
runtime identity, so ordinary recovery can finish an interrupted cross-owner
replacement without repeating `--transfer`. The exact prior receipt bytes stay
available for ordinary-failure rollback; they do not remain the journal's
recovery owner. Edited intermediate commands and callers from another owner
remain blocked.
Nested intended-receipt sections are structurally validated before use; a
corrupt journal is preserved and reported without aborting unrelated projects.
After proven lineage admission, an intended receipt may retain the journal's
recorded owner and version for either supported resolver. Recovery checks its
exact payload-local or user-side template and hashes, completes the admitted
transaction, then allows ordinary reconciliation to migrate the shortcut.
An unrelated intended owner is never admitted.

Results retain `migrated`, `removed` and `preserved`. `blocked` identifies
unresolved **required** commands: registered commands (including knowledge-only
retirement) and admitted-owned obsolete commands whose retirement remains
unfinished, even after unregistration. Recovery retains required status once
the pending transaction's ownership and structure are verified; publication
errors or edited intermediate bytes cannot turn owned cleanup into advisory
inventory. Unrelated foreign or ambiguous unregistered inventory remains advisory in
`preserved`. A required blocker suppresses the “in sync” message. Consumers
must use `blocked`, not assume that zero changed files proves convergence.
An unchanged second pass leaves both command and receipt timestamps untouched.
