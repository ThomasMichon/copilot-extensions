## Native providers available on main; caller publication is provider-first

- Verified all 20 effective #14393 paths on pinned `main`
  `01ce2b60ef59061bfd4984f31409f46cc1ebb99b`: 17 exact matches, two version-only
  metadata changes and four unrelated generated source-fingerprint refreshes.
  The five native resources match the qualified merged bundle exactly.
- Stopped native-provider release observation. Neither source release proves
  installation, package-registry publication or running-system adoption.
  The unchanged Process Telemetry version alone cannot distinguish the older
  Python-only provider from the actual native resource closure.
- The portable provider implementer returned the unstarted native-only
  publication slice without source changes. The driver now owns that shared
  materializer and Node integration; the adopter integrator keeps its separate
  repository allocation and can consume the verified released provider.
- A real publication seam is required for native-only payloads: Invocation
  manifests do not automatically stage assets for independent Node commands.
  Use an explicit consumer declaration, a complete versioned five-file closure
  and a selected descriptor, not a fake Python runtime or global-root lookup.
- Publish and release the trusted materializer before the Node declaration.
  Protected-main tooling can execute against newer source; one source PR with
  both sides would not prove the executing publisher understands the new form.
- Static consumer cause declarations preserve existing safe classifications.
  They are compiled into the closed catalog, never accepted as runtime message
  text or an argument/exception archive. This is an implementation choice under
  the original Goal, not new collection authority.
- Caller coverage, remaining families, installed qualification and all broader
  Plan/Validation gates remain open.
