## Received Plan

### Track 1 — Rightful continuation and paired readiness (predecessor #2467)

- [ ] Investigate how a finalized worktree can remain actively resumed, including the reported child-scoped finalize/parent-CWD hypothesis without treating it as established cause.
- [ ] Support an explicit continuation/reactivation decision by the rightful source owner, or refuse a genuinely retired resume before activation. Preserve source/target acknowledgement, qualified project/session identity, durable history and lineage, legitimate new-child/obligation capacity, and existing claims without `--no-owner` or automatic reacquisition of released resources.
- [ ] Distinguish paired-sibling relationship from usable checkout readiness. A positively missing sibling is different from unreadable, unavailable, or remote-unknown evidence. Preserve pair ID, complementary roles, reciprocal identity, and unknown-state holds; do not silently replace a pair or infer relinquished custody.
- [ ] Preserve the inherited detached/background behavior: inherited CWD must not implicitly reactivate a finalized checkout, and the actual background spawn/workspace owner must supply the repository-root CWD fallback. Keep that behavior distinct from the lifecycle recovery decision.

### Track 2 — Cross-project effort binding (predecessor #2475)

- [ ] Resolve a relative effort README against the paired knowledge state root when operating from a stateless harness.
- [ ] Resolve the intended worktree record and perform bind/show/release and duplicate-binding bookkeeping under the target worktree's owning tracking authority, even when invoked from another project or CWD.
- [ ] Preserve canonical project and worktree identity, ambiguity refusal, README containment/link/reparse protection, and state-root failure diagnostics. An absolute README path or binding a different knowledge worktree is not equivalent to binding the intended harness record.
- [ ] Keep effort README schema-message friction as separate adjacent scope.

### Track 3 — First-session onboarding and provider-aware setup (predecessor #3004)

- [ ] **KO1:** On the actual first restarted model session after bootstrap/plugin installation, offer one actionable create/register-new OR bind-existing-adopted flow without configuration-file internals. Preserve explicit prior topology/selection and knowledge versus executable-harness roles. Decline leaves the harness explicitly unbound; stateful operations fail closed with actionable diagnostics and no fallback into another repository. Permit legitimate machine-local setup writes. Use current source-owned/session guidance rather than a retired aggregation hook.
- [ ] **KO2:** Offer binding as a normal setup phase after core prerequisites. With no prior choice, present the consuming harness's conventional private-repository candidate as a safe preselected default; preserve confirmation and existing checkout, remote clone, dedicated repository, and advanced/provider alternatives. Generic guidance remains repository-name-neutral; this is not compulsory binding or a new identity store.
- [ ] **KO3:** Expose and consume one shared non-mutating registration/landing-policy preflight before auth selection or local default-branch mutation. Distinguish canonical registration, fallback, unresolved, and unverified discovery; resolve canonical remote/provider and scoped account; report effective server landing mode only when proven, with explicit unknown, insufficient-permission, and unsupported states. Do not equate direct-commit defaults or writable-account readiness with server policy.
- [ ] **KO4:** If a push is rejected after local mutation, preserve commits and offer the provider's bounded supported recovery. No reset, data loss, force push, policy bypass, ambient-identity mismatch, or global account switch.
- [ ] **KO5:** For a new GitHub knowledge repository, after the first push establishes the default branch, create or verify active deletion and non-fast-forward/force-push protection for that branch. Recognize equivalent protection idempotently; do not add a PR requirement or agent-usable bypass, and leave ordinary direct/fast-forward writes and separately unprotected feature branches usable. For adopted GitHub repositories, report equivalent/missing/unknown protection and a recommendation rather than rewriting policy automatically.
- [ ] **KO6:** Use repository-scoped GitHub identity. For non-GitHub providers, provide an equivalent implementation, an explicitly tracked follow-up, or unsupported readiness; do not block the bounded GitHub safeguard or imply unsupported repositories are protected.

### Track 4 — Paired convergence and recoverable removal (predecessor #5543)

- [ ] **PF1:** Resolve empty-companion convergence through a separately owner-reviewed safe cascade OR cleanup-policy revision, including stranded pairs. Until that policy is accepted, preserve BOTH-finalized removal and explicit-unused retention. Do not infer sibling finalization or remove the gate merely for convenience.
- [ ] **PF2:** Inventory reciprocal registrations, checkout paths, branches, refs, and pair identities in both repositories. Protect dirty, untracked, unlanded, claimed, followed-up, or live-session content. Finalized does not mean stopped; missing checkout, failed query, unreadable/foreign record, and unknown remote state remain holds. Preserve the unlanded-companion warning/block concern and credit the bounded paired-claim safety slice only for what it delivered.
- [ ] **PF3:** Make eligible physical removal atomic OR resumable. Complete fetch/landing/HEAD and other required safety checks before destructive teardown; retain the original needed-locks-first OR linkage-last alternatives. Git-lock contention must not strand a partially removed tree without supported recovery.
- [ ] **PF4:** Preserve accurate finalizing/incomplete/retryable custody after failure, including when Git pointer/admin data is already gone. Repeated lock, fetch-timeout, and uninspectable-HEAD failures remain diagnosable and recoverable through supported idempotent finalize OR repair, not manual directory deletion.
- [ ] **PF5:** For Windows locked/inaccessible residuals, report the actual failing operation/path/probe with bounded retry OR an exact actionable hint. Separate structural emptiness, readable-content proof, and accessibility/lock proof. An inaccessible descendant is UNKNOWN, not disposable cache noise.
- [ ] **PF6:** Revalidate both lifecycle/pair identities, ownership, content, liveness, claims, refs, and accessibility under existing ordered locking at the action boundary. Preserve residual branches, partial outcomes, and the last authoritative recovery record until exact owned, content-safe removal is proven. Concurrent changes must not race a stale idle decision.
- [ ] **PF7:** Distinguish tracking-only retirement, verified complete physical absence, and incomplete removal in structured and human results. Keep success/exit/warnings/removed semantics coherent; do not claim physical success from an intermediate stage or confuse deliberately retained unmanaged content with failed or fully deleted managed content.
- [ ] **PF8:** Preserve incumbent source/resource/implementation owners, assignments, claims, holds, and activation gates. Existing live-CWD-holder deferral and report-only documentation are partial credit, not full recovery. No age-only lock clearing, elevation, ACL reset, process kill, force removal, manual cleanup, or new tidier is authorized by this tracking intake.
