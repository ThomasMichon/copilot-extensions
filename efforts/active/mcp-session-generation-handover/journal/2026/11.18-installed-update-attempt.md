# Installed Windows update attempt and refusal diagnostics

Back to the [effort](../../README.md).

## Ordinary update, artifact repair and independent outcomes

A real ordinary Windows update delivered MCP `0.2.293-dev1` to
`0.2.299-dev1` while the explicitly selected native-client fixture remained
connected. No installed package or capability declaration was patched.

The first full update failed after healthy Dispatch coordinator cutover:
the generated coordinator launcher could not be atomically replaced because
the file was in use. This is the existing [#11875](https://github.com/ThomasMichon/copilot-extensions/issues/11875)
boundary, not a new source claim. Native execution took 755.271 seconds;
original invocation to completion took 819.770 seconds. Those intervals overlap
and must not be added.

After that request became terminal, the authentic selected publisher restored
the generated artifact under its activation mutex, with source, selection and
inspected-before comparisons. Its optional predecessor-retirement fallback was
disabled. Exact rendered bytes and the real `-ResolveOnly` consumer agreed.
The installed publisher matched the promoted source after CRLF normalization,
not raw-byte equality. The original failed update remains failed.

A subsequent ordinary validation acquired Worktrees `1.27.46-dev1`. Its
incoming monitor was healthy and published, but the lifecycle returned one and
the frontend exposed only a generic failure. That is not proof of the specific
refusal cause. After independent current-selection, native-readiness and
queue-settlement checks, one idempotent retry completed successfully: 188.288
seconds of native execution and 241.499 seconds from invocation. This passing
retry does not erase the two earlier failures or qualify a clean first-attempt
under-five-minute update.

## Installed MCP attempt: partial evidence, not handover acceptance

The actual native client consumed its initial synthetic tool result through
installed MCP `0.2.293-dev1`. Its creation-bound owner, physical receiver
processes, keeper and upstream remained alive across the failed update, artifact
repair and successful validation. Synthetic caller context stayed in memory.

After the final update result, a fresh installed physical entry executed a
real synthetic tool call through the incoming `0.2.299-dev1` shared backend,
not a cold fallback. The upstream's actual parent was that backend. Incoming
version and admitted source-prefix checks passed, and the original backend
was observed dead.

The fixture then failed its exact daemon-count assertion, which counted
registry rows marked `running` rather than independently classifying their
native PID/birth states. The rows were not captured at that boundary, so a
stale record is a possible explanation, not a confirmed diagnosis or proof
that only two live daemons remained. The subsequent original-client tool call
did not run. **Installed Windows session-reattachment acceptance remains open.**

The native client exited through its ordinary input boundary. All measured
fixture processes were subsequently absent, and all 56 original native-client
identities remained present. This does not substitute for the missing
post-retirement exchange or make abrupt client-owned MCP settlement graceful.

The next attempt needs a typed native process census before asserting the
live-daemon set, preserving unknown identity as a refusal. It also needs a
genuine later installed generation change; re-running an unchanged installation,
fabricating a version or replaying the completed update is not equivalent.

## Bounded frontend correction

[#13321](https://github.com/ThomasMichon/copilot-extensions/issues/13321)
tracks the independently confirmed diagnostic loss. The Python lifecycle
writes a structured settled refusal, but the PowerShell frontend threw on its
nonzero exit before reading that result and then removed the result file.

The matching Bash frontend also removed the result before exposing its reason.
Both native frontends now read only a valid version-one refusal, preserve its
specific reason and committed-publication disposition, and keep the original
nonzero failure. Malformed results retain the generic diagnostic. Native Bash,
PowerShell 7 and Windows PowerShell 5.1 controls cover the boundary; the
PowerShell controls reproduce the lost reason
before the correction and verify committed/uncommitted refusals, malformed
results, existing successful completion and stderr streaming afterward.

This is diagnostic source qualification, not a diagnosis of the original
refusal, installed validation of the correction, or effort completion.
