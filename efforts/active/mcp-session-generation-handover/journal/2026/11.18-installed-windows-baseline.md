# Installed Windows native-client baseline

## Result

A bounded, private-namespace baseline passes using the installed MCP
`0.2.293-dev1` runtime and native Copilot `1.0.114-0`. The real native client
consumes two distinct tool results after the creation-bound snapshot publisher
has exited. The same client, custody keeper, upstream and backend retain their
native identities through both exchanges. All 56 measured pre-existing client
incarnations remain alive afterward.

This is installed baseline acceptance, not an installed update or handover.
No version selector changes, production caller enrollment, credential access
or production upstream calls are part of the fixture. The effort remains Active.

## Actual installed path

The fixture imports MCP from the selected installed application's nested venv,
not the source tree or a constructed replacement runtime. The installed
`windows_overlay`, anonymous native section implementation and physical optional
receiver are used without a copied-capability override or package edits.
Native client creation uses the installed Worktrees suspended-creation owner.
The publisher supplies the actual child's creation-handle PID/birth and exits
before ACP initialization and delayed MCP startup.

A credential-free loopback canned provider selects two unique synthetic tools
and verifies that Copilot consumes their real results. The upstream ledger
records one initialization, each accepted nonce exactly once and the custody
keeper as its actual parent. The backend reports the selected installed MCP
generation through the fixture's private authenticated endpoint.

The fixture uses isolated home/configuration/serving paths and the existing
contained, leased test lifecycle. It does not patch installed code, add a
production configuration, start inference or invoke a real configured service.
It is a composition of the existing
[native-client ownership packet](11.10-explicit-owner-cli.md#windows-native-client-consumption-source)
and the earlier
[installed Linux baseline](11.10-explicit-owner-cli.md#installed-portability-baseline),
not a new default launcher.

## Settlement and corrected fixture assumptions

Closing the original ACP input lets the native client exit naturally. Before
lease cleanup, the original upstream and both registered daemons are already
dead and the anonymous owner section is absent. Both instance cleanup receipts
settle, with no unconfirmed pre-existing client identity.

The upstream Python finalizer does not run. This is native-client-owned abrupt
MCP settlement, **not graceful upstream EOF**. The distinction matches the
existing Windows native-client source qualification and remains visible rather
than being converted into an EOF pass.

Earlier attempts are not passes. An admission comparison first confused the
slot's `-dev1` spelling with Python metadata's normalized `.dev1` spelling.
A subsequent functional run incorrectly required the Linux EOF disposition.
Another fixture check mistook the Windows venv redirector for the upstream's
custody parent; the stdlib-only synthetic upstream now uses the physical base
interpreter, without changing MCP's installed runtime. Each actual fixture
settled before the next attempt.

Native version observation uses the same isolated environment as the fixture.
An inherited CLI distribution override can make an otherwise identical
executable report an older version; an ambient `--version` result is not the
fixture's version proof.

## Remaining acceptance

An actual authorized installed-generation change must still be bracketed by a
held original native client and a simultaneous fresh literal MCP invocation.
Require original session/upstream identity, incoming physical-generation
execution, independently observed predecessor retirement and exact settlement.
Do not substitute this baseline, the Linux update result or source-constructed
Windows replacement packets for that evidence.

Production lifetime, default caller adoption, multiple-client behavior,
rollback, accepted/in-flight/unknown outcomes and the broader Plan and
Validation Plan remain open. Direct/resident primary-consumer parity is also
separate: an HTTP/dynamic-auth configuration can select the direct path for
both default and `--no-serve` calls under the existing bounded sharing policy.
