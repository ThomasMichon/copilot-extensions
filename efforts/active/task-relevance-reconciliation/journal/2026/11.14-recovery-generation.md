# Retain closeout generation during strict recovery

Back to the [active effort](../../README.md).

## Reproduced gap

A claimed task with no native attachment can accept source obsolescence while
strict recovery still considers its reset or agent detachment admissible.
All three strict recovery operations advance the task generation. They could
therefore leave the accepted original-owner closeout behind a generation fence,
even though ordinary claim/start admission continued to refuse the obsolete goal.
Diagnostics taken before that closeout also retained the same recovery revision.
Six supported-API regression cases reproduced these effects before the fix;
they require no raw queue writes or native effects.

## Bounded correction

The existing recovery snapshot now includes the task's retained relevance
closeout. Strict diagnostics and effect-time recovery refuse a pending
acknowledgement before advancing generation. A closeout accepted after inspection
invalidates the earlier opaque revision. Previously committed recovery requests
still replay their original receipt without another mutation.

This closes a source-level preservation gap under Phase 2, not the complete
owner-recovery gate. Legacy same-generation reset, original-owner readiness,
finalization acknowledgement and all native retirement guards remain unchanged.
There is no new endpoint, schema migration, recovery token, owner transfer,
cross-generation acknowledgement or automatic cleanup.

## Validation and limits

The named focused packet passes 24 tests covering the new refusal and stale
diagnostic cases, committed replay, existing strict recovery and HTTP authority.
A separate five-case preservation packet passes existing same-generation
requeue, claim readiness, finalization and lost-response replay controls.
Both use the contained runner and the same bounded supervisor; neither is an
installed or native lifecycle qualification.

An earlier seven-file packet exhausted its supervisor execution allowance
before producing a complete result. Anonymous progress could not establish
reusable named outcomes, so it earns no pass. The follow-up selections were
narrowed and retain named outcomes, phase durations and JUnit instead of
repeating the broad packet or increasing its allowance.

The optional devcontainer wrapper was not used: its declared 14-GiB/512-PID
outer resource profile exceeds this selection's two-GiB/256-task budget.
The source-owned contained runner retains redirected test state and process
containment; this is not equivalent to an OS-level filesystem/network boundary.
No native process, production task, service or allocation setting changed.
