## Source boundary

Direct worker registrations retain the existing complete version-1 definition
inside their existing spec JSON. Eager validation binds it to the actual
registration ID, execution machine, environment and cap before an insert or
upsert. No priority or permit/reject semantics are guessed for legacy rows;
an incomplete effective worker still withholds the whole pool snapshot.
There is no second registry, timer, executor or execution authority.

The existing client discovers the running provider's additive
`registration_definition_versions: [1]` and uses the distinct
`/registrations/pool-definition` write route with the same registration body,
writer and ordinary authorization. Old providers refuse that route even if
rollback happens after health discovery; the client never retries through
the permissive legacy path. Legacy registrations keep their old path and
meaning. The existing CLI `--spec` path reaches this client unchanged.

Effective-source reconciliation reads the stored definition and preserves
pause/resume and concrete/logical vetoes. A declaration supersedes an explicit
direct row only when both runtime behavior and complete normalized pool policy
match, ignoring only the differing registration ID. Otherwise both capacity
owners survive. Confirmed declaration withdrawal restores the retained direct
row; a pending withdrawal remains unavailable, not prematurely complete.
Metadata-only changes invalidate catalog inputs without restarting the legacy
child or changing its argv.
