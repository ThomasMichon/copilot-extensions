## Linux implementation candidate

The implementation candidate reuses the existing Python inventory, lock,
process-birth and artifact owners. Its gated child group and libc subreaper
retain owner-loss expiry, monotonic renewal/hard bounds, unreaped-child identity,
reparented-descendant settlement and the matched settlement witness. Optional
Python pidfd wrappers use the existing libc interface when absent; neither path
compiles code or substitutes numeric-PID signaling.

The canonical C source, fifteen generated copies and old build module are
removed. Pure-wheel construction and source verification no longer build or
admit an ELF. Shell callers use one deterministic, source-only Python archive
covering the complete import closure; the normal generator publishes the same
archive to package and payload consumers with explicit file custody.
Production admission remains direct and non-expiring. Unsupported or missing
lifecycle facilities retain held records and diagnostics.

Local qualification covers the complete shared library suite, source/archive
and release-owner controls, and actual installed-interpreter lifecycle tests.
A fresh, compiler-absent box built and source-verified the pure wheel without
introducing a compiler. A separate network-disabled box passed all six
source-lifetime and installer-reclamation assertions. These are distinct
construction, installed and source-consumer checks, not production rollout.

The candidate still owes source review and merge. Windows embedded compilation,
runtime code emission and genuinely pre-Python bootstrap are not replaced by
this Linux slice. Their interpreter, Job, pipe and filesystem-custody gates
remain open under the same amendment; the effort is not Done.
