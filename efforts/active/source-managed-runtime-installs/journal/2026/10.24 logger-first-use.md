## Boundary and existing custody

Continue the same Installation execution implementer under #7758 using the
existing foundation, canonical queue/results and frozen-input owner. Preserve
core/schema, normal/repair, source/adopter/native/deployment and maintenance
custody, #7030 publication and #8370 installer diagnostics. Public dedup found
no competing Logger recipe implementation; the unrelated metrics contribution
is not superseded. Keep all retained #2822/#4010/#4015/#4058 parent acceptance.

Logger's version-2 payload declaration names six fixed command/module pairs,
requires installation context and declares installer lifecycle, but has no
top-level command/module or provision mode. Preserve that multi-command shape,
bespoke native gates and own `AGENT_LOGGER` controls rather than rewriting it
to resemble another plugin.

Both native provision actions construct/activate the package/runtime and write
the deployment manifest. They do not register the separately installed sync/
prune task or timer. Stamp publishes a versioned snapshot and the primary plus
five compatibility commands; default-root equality, not merely an omitted
InstallDir argument, determines global versus scoped command publication.
There is no Vault service-option contract to copy.

## Proposed implementation and qualification

Extend only the fixed recipe roster, own projected context and canonical
freezer projection where needed. Admit the canonical installed payload and
default legacy root; retain exact source/project/publication admission, clear
foreign action/payload/validated hints and use native staged-origin custody.
Invoke only Logger's actual fixed native stamp or provision options. Do not
introduce another queue, schema, scheduler, arbitrary argv or foreground
fallback. Review and merge this proposal before implementation.

Use the existing manual Windows/Ubuntu installation-context portfolio, not an
exhaustive addition to required PR CI:

- Prove Python and native no-write rejection for unsupported declarations,
  copies/snapshots, custom roots/cells, client-only options, managed publication,
  no-self-provision, pins and nested execution before acquisition/queue/plugin
  writes. Keep healthy non-publication dispatch unchanged.
- Verify exact own context projection, foreign-hint clearing, canonical native
  arguments, typed request identity/coalescing and durable nonzero outcomes.
- Exercise actual materialized native stamp and cold provision, selected
  immutable command/module/distribution/build identity, complete dependency
  closure and failed-candidate preservation. Qualify raw-checkout dependency
  mapping and installed source independence rather than assuming fixture
  materialization proves either boundary.
- Run safe real installed help/version/status consumers for the declared
  commands without processing personal sessions. Credit only the consumer
  surfaces actually exercised; metadata/import identity alone is not CLI health.
- Prove Python-free caller loss and concurrent cold submitters use the same
  canonical authority and ordinary durable receipt/result on both native lanes.
  Retain applicable Vault/Pull Requests/SSH/CodeSpaces recipe regressions.
- Assert no sync/prune task/timer registration or personal logging effects from
  stamp/provision. This is service-less recipe evidence, not qualification of
  explicit install/update registration or a live periodic worker.

Selected snapshots, compound actions, primary/auxiliary/payload command
publishers, bootstrap, explicit installers, task/timer adoption, cells/custom
roots and host rollout remain open separate slices. No personal sync/prune,
task registration, enrollment, deployment or conversation scrub is authorized.

This closes part of the existing Installer/Plugin Service Model execution-owner
intent using the single-owner, thin-adapter and cross-platform patterns; it
does not extend standing intent or create a competing installation authority.
Documentation impact is this ROOT row and dated matrix; as-is runtime docs
change only after the actual implementation.
