# Azure DevOps PR description completeness

Back: [Incremental Indexing Delta Pipeline](../../README.md).

## Bounded correction

Issue [#13305](https://github.com/ThomasMichon/copilot-extensions/issues/13305)
tracks a Phase 3/provider-compatibility correctness gap. The documented
[project PR-list API](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-requests/get-pull-requests-by-project?view=azure-devops-rest-7.1)
truncates descriptions to 400 symbols, but the connector previously rendered the
listing object directly. This is vision-closing complete acquisition, not a new
query language, provider protocol or indexing engine.

The connector now point-acquires an eligible, deduplicated PR at the ambiguous
preview boundary through the configured project's documented PR-by-ID endpoint.
Conservative UTF-16 accounting also covers astral-character previews. A short
description needs no additional request. The detail response must retain the
selected PR/repository identity and contain a string/null description; only
that description replaces the selected listing metadata. Invalid/unavailable
details refuse acquisition without falling back to the preview.

The existing counters retain the listing preview as a returned body record and
observe the point response as another body, not another listing identity.
Request purpose, returned records and admission remain separate. Existing
comment rendering, query eligibility and deduplication are unchanged.

## Qualification

A new focused file avoids growing the existing 900-line connector test module.
Its initial seven cases give six intended failures and one passing short-body
control before the source correction. The final eight controls cover ASCII and
UTF-16 preview boundaries, complete and cleared descriptions, wrong PR/repo,
missing body and HTTP refusal. Exact request sequences and parsed/request
counts forbid extra enumeration and comments after failed detail acquisition.

The combined bounded selection passes **57 cases** across the focused controls,
existing Azure DevOps connector and shared HTTP tests, with verified cleanup.
Whole-file strict analysis passes for both changed Python files on the
configured Linux and Windows targets; native execution was Linux. High-signal
Ruff and the 13-plugin install contract pass. Checker preparation required the
established Python 3.13 interpreter; no dependency pin or project admission was
changed.

## Remaining gates

Normal review, merge and publication are still required. This correction does
not qualify PR modification-time discovery, documented offset pagination,
durable query progress, immutable membership, authoritative tombstones or
live-provider behavior. Those remain under this Active effort's existing
provider/count and correctness-owner gates. No live service or credential
operation was performed.

## Review correction and performance impact

The first review found cancellation missing between the new point read and
comments, missing/nontext listing descriptions bypassing validation, a
validator-only cache allowing a bodyless 304 on a reused connector, and the
missing performance assessment. Four regression failures reproduced the three
runtime defects before correction (missing and numeric descriptions are separate
controls). The source now rechecks cancellation before comments, refuses
missing/nontext listing descriptions while preserving explicit null, and
requests point descriptions unconditionally. No stale body cache is invented.

The parsed-pull fixture moved into the focused body-contract file. It retains
all previous metadata, listing, parsed-body, duplicate and ID-only counts while
expecting the newly required refusal. Required whole-file checking also exposed
annotation gaps in the touched older test module; annotations and runtime type
narrowing resolve them without ignores, admission changes or weakened assertions.
The final packet passes **63 cases** with verified cleanup, whole-file strict
analysis for all three changed Python files on Linux and Windows targets,
high-signal Ruff, focused-file formatting and the 13-plugin install contract.
Native execution remains Linux-only.

The caller is each legacy full or timestamp-filtered Azure DevOps discovery
round. For `L` listing-page requests, `P` eligible unique PRs, `D <= P`
possibly truncated descriptions and `C` existing comment-page requests, the
ordinary successful HTTP-attempt count is `L + D + C`, excluding existing
metadata and retry attempts. The point-read work is proportional to the
selected boundary-size bodies, not an added history scan. Missing/nontext
bodies stop before comments. Detail reads remain serial and use the existing
throttle/retry owner; no subprocess, installation, tree, store or embedding
work is added. ID-only discovery does not point-hydrate descriptions.
At the default 0.2-second request spacing, 1,000 boundary-size selected PRs
mean 1,000 additional reads and approximately 200 seconds of added spacing,
before provider latency and retries. This is a conditional cost projection,
not a measured native workload or a claim that the legacy scan is delta-bounded.

Deterministic fixtures measure one listing plus one comments request for a
short body, and one additional point request for a boundary body. Two rounds
on the same connector each make all three requests and retain complete text
despite a supplied ETag. Filtered and duplicate previews add no point requests. Conflicting detail
metadata cannot replace the original listing title, status, source or repository.
Cancellation after the point read makes two requests and no comments request.
There is deliberately no response-body reuse: the HTTP owner's validator cache
cannot certify available text. A future complete-body cache would require
identity/revision validation and explicit invalidation before conditional reuse.

under the caller's bounded test supervisor. For an explicitly authorized native

and end-to-end monotonic duration, and record provider cardinality, retries,
OS and cache conditions. No native provider credentials, network run, cold/warm
latency distribution or CPU claim is supplied by these transport fixtures.
Live-provider qualification remains with this effort's provider-matrix owner;
unit elapsed time is not a provider-latency measurement.
