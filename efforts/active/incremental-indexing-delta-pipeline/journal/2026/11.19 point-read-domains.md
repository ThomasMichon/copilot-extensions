# Exact point-domain binding and default refusal

The existing source-layout owner now has an in-process cold binding seam for
one exact `PointChangeHints.scope`. Protocol 2 retains the source, component
family, account and complete `PointBinding`; protocol 1 keeps its existing
meaning. Reopening and receipt publication refuse a different selection or
downgrade. Cached handles include the selection instead of lending an explicit
point binding to a later default opener.

Default store constructors refuse the new protocol. Nested and lazy selected
reads check the current receipt, and unmarked legacy handles refuse a later
marker before reads or writes, including direct vector access and sibling
cluster state. This last case matters even for an empty directory opened
before cold initialization. It uses the existing operation decorators rather
than a second read engine. The cluster constructor retains its lazy Lance
import through `import_module`, so its changed whole file can be checked
without requiring native storage dependencies in the typechecking environment.

Four small in-memory controls cover receipt/protocol/scope/refusal behavior in
required unit admission. Initial separately selected native qualification passed 37
cases, including all existing source-aware-store controls and four new cold
point-domain cases; the four unit controls also pass. Test-supervisor reports
verified descendant cleanup. Whole-file strict checking passes for all four
changed Python files on Python 3.10/Linux and Windows targets; Ruff passes.
The install contract passes for 13 plugins. These are local results, not
native Windows execution or installed-runtime qualification.

This closes only the binding/default-refusal foundation. Even exactly selected
point handles refuse the existing legacy-shaped read, operation, write and
reconciliation APIs. Explicit component results and applied-version/read-route
qualification still precede v2 execution. Both parent plans remain Active;
current-claim application/completion without polling advancement, unknown
native effects, mixed restores and broader consumer/count qualification stay
open. There is no live allocation, activation, migration, deployment or rollout.

## Receipt ambiguity and caller-directory independence

The first review identified two concrete bypasses: a relative `_db_path` could
retarget the late-marker check after `chdir`, and last-key-wins JSON could
disguise protocol 2 as protocol 1 for an unselected reader. All receipt readers
now reject duplicate fields before protocol interpretation. Content, combined
and direct vector guards use the native connection's already-bound URI;
clusters retain an absolute sibling-domain path. This reuses the actual
connection owner rather than creating another path-binding registry.

The native late-marker control now covers both absolute and relative opens
followed by a caller-directory change, across content, vector, combined and
cluster reads plus an empty write. The in-memory controls cover both duplicate
protocol orders for default and explicit handles and connection-URI precedence.
All 38 selected native cases and four unit controls pass with supervisor cleanup
verified; strict Python 3.10 Linux/Windows targets and Ruff pass again.
Required current-head review and CI remain separate gates.

and Ruff pass again. No additional reader, executor or rollout is enabled.

the native connection's already-resolved URI for all later path uses.

The regression builds a real FTS index through the contained child after a
relative open and caller-directory change, verifies original content is
searchable, and leaves every marked-destination file unchanged. All 40
selected native cases pass with supervisor cleanup verified. The unchanged
