# Ordered chunk-failure checkpoint recovery

## Existing checkpoint-owner qualification

- Follow #4222's original failed-content/retry outcome rather than creating a
  second cursor authority. The current shared file batcher already propagates
  chunker failures in both layouts. The historical legacy warning/continue
  branch is not the current implementation.
- Extend the callback-level direct batch control with a later-file chunker
  failure after an earlier whole-file store/cleanup acknowledgement. Its
  path-index checkpoints use real SQLite. The source cursor
  must remain old; only the earlier proven file checkpoint may be reused on
  retry. The failed file must be attempted again before publishing the target.
- Add native dual-model controls in both layouts with a real prior committed
  source. Failure chunking the second file must preserve exact source-state
  bytes, file checkpoints, native versions, selected receipt and retained
  content. The first file's prepared vectors remain subordinate to the pinned
  acquisition. Reopening state/path-index objects must reuse those vectors,
  embed only the failed second file, finish the old acquisition, then discover
  a newer delta. Exact document/vector inventories are checked after retry.
- The full-rebuild control starts with compatible existing checkpoints but
  still requires first-file chunking/embedding. A later chunker failure keeps
  the old committed source usable and retains the manifest's full flag.
  An ordinary retry must finish that full acquisition before a fresh delta,
  without interpreting the failure as an empty successful source.
- The strengthened two-file packet passes 62 tests with nine existing explicit
  skips. All new native controls run in both layouts. The earlier three-file
  packet also passes 62 tests with nine skips, including the unchanged
  task-window/batch resume controls. Touched-test typing and Python lint pass.
- This is qualification of the existing runtime behavior, not a new layout,
  full-reindex request, checkpoint migration or recovery permission. #4220's
  durable source exclusion/alias watermark consistency remains open, as do
  reader/vector-coverage coordination and the overall effort's other gates.
